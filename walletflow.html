ENGINEERING DECISIONS

Simple choices that make the project easier to trust and maintain.

Explicit column selection

The models avoid SELECT *. Each CTE selects only the fields required downstream, which makes schema changes more visible and model contracts easier to understand.

select transaction_id, customer_id, amount_ngn, status, created_at from {{ ref('stg_transactions') }}

Testing & data quality

Tests cover primary-key uniqueness and nullability, accepted values, positive transaction amounts, customer relationships and completion timestamps for successful transactions.

Reusable business logic

Transaction status flags and daily activity logic are defined once and reused in downstream marts so analysts do not repeatedly redefine the same concepts.

BI-ready outputs

The final mart exposes governed definitions for transaction count, successful transactions, GTV, success rate, fees and active customers. A BI tool can consume this layer directly.

INTERVIEW VERSION

How I explain WalletFlow in under a minute.

“I built WalletFlow as a synthetic fintech analytics engineering project. I generated customer, wallet and transaction data, then structured it into staging, intermediate and mart layers. I explicitly selected columns, standardised data types and statuses, built reusable fact and dimension models, added data-quality tests, and created KPI marts for transaction performance and customer activity. The idea is that BI teams can query governed models instead of rebuilding metric logic in every dashboard.”
